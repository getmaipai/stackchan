# Every check that rejects a bad update image (2026-11-18)

One table for the whole update path: what makes it, what serves it, what the unit checks, and the web flasher. "Through the unit's code" means the firmware's own C and C++ files compiled for the PC and run (`update_verify.cc`, `maipai_updatehdr_core.h`); the new `host/tests/test_update_path_rejections.py` builds a package and an image for each row, asks the unit's code and the host's code, and requires that they agree and that the unit gives the reason named here.

## The checks, in the order an image meets them

| # | Check | Where | Rejects | Tested by |
|---|---|---|---|---|
| 1 | The release key is a file the owner holds; a real release needs a build number higher than the last | `scripts/release.sh` | a lower or equal build number, a missing key, a damaged last-build file, a key-shaped value in the folder, a folder that already holds files | `test_release_and_update_vectors.py`, `test_cross_review_open_bugs_2.py` (fixed) |
| 2 | The release list is signed; the manifest, the app image and the 56 byte header each carry an Ed25519 signature that the script verifies right after making them | `scripts/release.sh` | a signature that does not verify | `test_release_and_update_vectors.py` |
| 3 | The host reads a release only with a trusted key, and only a signed, valid list whose parts match their hashes and whose app image leaves 20 percent of the smallest slot free | `bodies/stackchan/updater.py` | unsigned, no key, another key, an altered list, an altered or missing part, a preset mismatch, a full slot | `test_stackchan_updater.py` |
| 4 | The host serves the image with its `.sig`, `.hdr` and `.hdr.sig`, one read, to one paired unit | `xiaozhi/server.py`, `firmware_update.py` | a bad or missing signature, no trusted key, a hash that changed | `test_firmware_update_signature.py`, `test_stackchan_firmware_update.py` |
| 5 | The host's own header check, in the unit's order | `firmware/update_header.py` `verify_package` | a package that is not 120 bytes, a bad header signature, a header that is not a header, a length or hash that does not match, a build number not above the installed one | `test_update_path_rejections.py` (agrees with the unit on every row) |
| 6 | The unit takes the image only from its paired host | `update_verify.cc` `UpdateUrlIsPairedHost` | another host, a look-alike name, an address with user info, a scheme other than http and https | `test_unit_update_check.py`, `test_update_path_rejections.py` |
| 7 | The unit fetches `.hdr` (56 bytes) and `.hdr.sig` (64 bytes) exactly | `ota.cc` (SF25; device code, not run on the PC) | a missing file, any other length | the patch text is pinned in `test_update_path_rejections.py` |
| 8 | The unit has a trusted key built in | `update_verify.cc` `UpdateTrustedKey` | no key, a key of the wrong length, not hex | `test_unit_update_check.py`, `test_update_path_rejections.py` |
| 9 | The Ed25519 signature over the 56 header bytes | `update_verify.cc` | a changed signature (any bit), a signature from another key, a header changed after signing, an S above the group order, an all-zero signature or key | `test_unit_update_check.py`, `test_update_path_rejections.py` |
| 10 | The header: magic, reserved bytes, build number against the floor (the higher of the confirmed build and the one compiled into the image, SF37), build zero, build of 2^31 or more | `maipai_updatehdr_core.h` `muh_parse` | wrong magic, reserved bytes set, build 0, build 2^31 or more, a build not above the floor | `test_update_path_rejections.py`, `test_update_header_core.py` (shared vectors) |
| 11 | The image fits the slot | `update_verify.cc` `UpdateFitsSlot` | more than 80 percent of the slot, zero bytes | `test_unit_update_check.py`, `test_update_path_rejections.py` |
| 12 | The image's length equals the header's, before it is written | `ota.cc` and `muh_check_image` | an image longer, shorter (a cut download) or empty | `test_update_path_rejections.py` |
| 13 | The image's SHA-256 equals the header's, streamed | `maipai_updatehdr_core.h` `muh_check_image` | one byte changed, a wrong hash field | `test_update_path_rejections.py` |
| 14 | A new image must prove itself on its first boots, or the unit goes back to the old slot | `maipai_update_core.h` (FM01) | a crash loop, a stalled start | `update_core_test.c` through `test_firmware_*` |
| 15 | The web flasher: the page reads only its own site's list, the list is signed by a key pinned in the page, every part name and offset is plain and inside the flash, the downloaded files hash to the list, none is empty, none runs into the next or past the end of the flash | `flasher/flasher-core.js` | a list from another site, an unsigned or re-signed list, an encoded dot-dot, an absolute or data address, a query, an unaligned or out-of-flash offset, two files at one place, a changed file | `flasher/test/core.test.mjs`, `test_flasher_release_parity.py` (the page accepts what the release script signs and refuses every change), `test_cross_review_open_bugs_2.py` |

## What is not checked, said plainly

- **Wrong device.** The signed header holds a build number, a length and a hash, and nothing that names the board or the product. One release key signs every StackChan build, so an image built for another board of the same chip family and signed with that key would be accepted by the unit's header check; the boot loader's own image check only knows the chip. The paired-host rule (row 6) stops an image from an unpaired host, not an image for the wrong hardware. This is a decision for the firmware track (a board id inside the 8 reserved header bytes would close it); no test can assert a check that does not exist.
- **USB flashing and the build floor.** The web flasher writes the app image over USB; the unit's confirmed-build floor lives in its settings and is not touched, but an older signed release can still be written by hand. SF37 keeps the floor of the image that was flashed (the compiled build), which is the right fix for a newer image; an older signed release written over USB simply runs, because a person with the cable is trusted.
- **Header size and build number up to 2^32 - 1 on the host.** `build_header` and `verify_package` accept 2^31 and above, which every unit refuses (SF37): strict xfail `test_the_host_does_not_make_or_offer_a_header_with_a_build_number_the_unit_refuses`, owner app.
- **Device code.** The fetch of `.hdr` and `.hdr.sig` (row 7) and the first-boot trial (row 14) run on the unit; the PC tests cover the rules, the patch text pins the sizes.
