Placement: unit firmware (patches `G01` to `G03`, native lane) and the host side (`games.py`, one settings page section, one spoken path). Tree: `~/esp/stackchan-rebase/train7` (a copy of the Train 6 tree), ESP-IDF 6.1.1. This builds the design in `game-engine-note.md`, with one change of scope: the owner asked for the games to be in the core firmware, not only in the `home` preset, so the engine is behind `MAIPAI_GAMES`, default `y`, and the core preset turns it on (the memory gate passed, numbers below).

Where it is: the patches, the three game tables and packs, the compiler script, the host code, the tests and this note are uncommitted files in the working tree of this repo (not on GitHub `main`, in no release). The plain Train 7 image is flashed on the owned unit on the USB cable (sha256 `73bede8e67652511...a32883f`, 3,363,248 bytes, read-back equal to the build). Replaying `G01`, `G02` and `G03` with `git apply` onto the Train 6 files gives files byte-identical to the Train 7 tree. Nothing involves the Home hub.

## The pack

A game is data, never code. One pack is a header (version byte, counts, the counter that holds the score, a seed, a step budget), then tables:

- states, each with an optional timer (a fixed time or a random time in a range);
- touch regions (rectangles; always inside the screen edges the unit keeps for swipes, checked when the pack loads);
- shapes drawn in the shipped font and colors: fill, circle, rounded box, ring, text; each shows in a set of states, and optionally only while a counter has a value (a lit color, a mole in one hole);
- texts, English and Spanish, ASCII only, `%0` to `%7` print a counter;
- transitions: state, event (enter, timer, tap), the touch region or any tap, a guard (a counter test, "the tapped region is the next step of the sequence", "the tapped region is the one in this counter"), the next state (or stay, or end), and a short list of actions;
- actions: set, add, copy, random, elapsed time, divide, sequence reset, add, rewind and step, play one of five shipped tones, commit the score, copy the tapped region into a counter.

After the tables come a CRC-32 and, for a signed pack, 64 bytes of plain Ed25519 signature over everything before it. Eight counters, one 32 step sequence, 16 states, 96 rules, 255 actions at most: a pack cannot be larger than about 5 KB by its own limits, and the loader refuses anything over 16 KB.

The checker (`mg_parse`) refuses, with a sentence that says what is wrong and what to do (English and Spanish): a short file, a wrong first four bytes, a newer version, a wrong size, a bad checksum, a table over its limit, a reference to a state, counter, text, tone or region that does not exist, a letter the screen cannot draw, a region that reaches into the edges, a bad name. Nothing reaches the player before all of it passes.

The player runs at most 64 transitions for one event (a pack may set a lower number); the 65th stops the game and nothing is saved. One xorshift generator is seeded from the pack, or from the hardware random source when the pack names no seed, so the games are testable with a fixed seed on a PC.

### Signing

The rule is `mg_admit`. A pack inside the app image is covered by the image's own Ed25519 signature (patch 155), so it needs none of its own. A pack from anywhere else must carry a valid signature over the pack and its checksum, made with the update key and checked by the same `Ed25519VerifyDigest` code that checks firmware updates, with the digest built by the PSA crypto library as `UpdateVerifier` does. Without a signature it is refused (`unsigned`); with a signature on a unit with no key built in it is refused (`no key`); with a wrong signature it is refused. Only a bench build (`MAIPAI_GAMES_BENCH`) lets an unsigned outside pack run, and even a bench build refuses a bad signature when a key is present.

No shipped path loads an outside pack yet. The loader and every check exist and run (the bench tool calls them), but moving a signed pack from the host to the unit is the next step (the open questions below).

## The three games

All three draw with shapes only, run on the existing 30 ms LVGL timer that exists only while a game runs, and never move the head.

- **Color memory.** Four quarter-screen regions. The unit lights one with a tone, one step per light, then the person taps the steps back. Each round adds a step. A wrong tap ends the game. Score: rounds completed (higher is better). 8 seconds without a tap ends it.
- **Reaction time.** The screen is red for a random 1.5 to 4 seconds, then green with a tone; tap. A tap while red is "too soon" and the round is not counted. Three rounds; the score is the average in milliseconds (lower is better). No tap in 2 seconds counts as 2000.
- **Whack-a-mole.** Nine holes (nine touch regions). A mole is a circle in one hole for 0.7 to 1 second, 15 moles with a random gap. Score: moles hit.

Text is plain ASCII in English and Spanish (the screen font has no accents). Other saved languages read the English text.

How a game starts and stops:

- **By touch:** swipe down from the top, More, Games (a button per game with its best score; Juegos in Spanish). A refusal is written on that page.
- **By tool or voice:** `self.game.start` with `memory`, `reaction` or `whack` (or a title). On the host, "play memory", "juega a los topos", "stop the game", "para el juego", "what games do you have" and similar asks are answered by the host before the hub is asked (`head_commands.py`), and the hub commands `game_start`, `game_stop`, `game_list`, `game_scores` are wired beside the timer commands.
- **Stop:** a swipe down from the bottom edge, the stop word (not while the unit is speaking: then it stops the speech first, as before; a ringing timer takes the word before both), `self.game.stop`, full quiet, or an update starting.

Rules kept: the touch edges stay the unit's (a touch that began in an edge never reaches a game; the top swipe still opens quick settings, the side swipes still change the volume, the bottom swipe stops). No touch starts a listen or toggles mute, vision or full quiet while a game runs. Sounds go through `maipai_sounds_play`, so the sound policy, the night rule and the hard mute decide, and a refusal is silence. A mute plays the game with no sound. Full quiet refuses a start and ends a running game. A game keeps the screen awake while it runs.

Scores: the best five per game, in the unit's own NVS namespace `mp_games` (ten bytes per game), written once when a game reaches its end, on the main task (never the screen task). A game stopped early saves nothing; a score of zero is not saved.

## Memory and size

Unit: the owned unit on the USB cable, hard muted as saved (so no spoken turn, no camera, no real music), the unit's link to its host trying and failing in the background as before. Measurements come from the 10 second memory line of a bench build.

Images (app slot 5,177,344 bytes):

| Image | Bytes | Free in slot | Static internal RAM (DIRAM) |
|---|---|---|---|
| Train 6 plain | 3,341,632 | 35.5 percent | 165,483 |
| Train 7 plain (games on, flashed) | 3,363,248 | 35.0 percent | 165,659 |
| Games off, bench (compiled out) | 3,346,832 | 35.4 percent | 165,567 |
| Games on, bench with serial tools (shipped tool set) | 3,368,432 | 34.9 percent | 165,743 |
| Games on, bench with the four bench tools | 3,374,112 | 34.8 percent | 165,775 |

The games add 21,616 bytes to the plain image (the player, four tools, the pack tables and the Games page; the packs themselves are 3,796) and 176 bytes of static internal RAM. Compiled out, the image equals the Train 6 bench image to within 16 bytes.

Idle, no game running (steady internal free, three images from one tree, 130 to 150 seconds each):

| Image | internal_free steady | int_big | internal_min |
|---|---|---|---|
| Games off | 53,197 (median; Train 6 measured 52,711 to 53,171) | 31,744 | 39,828 |
| Games on, shipped tool set | 51,955 | 31,744 | 39,828 |
| Games on, with the four bench tools | about 50,500 | 31,744 | 39,828 |

So linked but off costs 1.2 KB of steady internal RAM: four registered tools (each holds its descriptor strings and property list on the heap). That is a little over the rule's "about 1 KB" for an optional feature that is off, and it is the tool table, not the engine: the engine holds no heap, no task and no timer until a game starts. A game that is not wanted is compiled out by `MAIPAI_GAMES=n`.

While a game runs: color memory costs 2.4 KB of internal RAM (LVGL objects: 13 shapes), whack-a-mole 4.1 KB (24 shapes), and 492 bytes of PSRAM for the game record; all of it is returned when the game ends.

Memory gate, bench image, 684 seconds of serial after a clean boot, with a bot playing the three games in turn (24 games started and ended, 15 scores saved, 275 tones asked for) and the status tool read between taps. 69 heap lines after the boot line:

| Measure | Gate | Observed |
|---|---|---|
| internal_free, steady with a game running | at least 25,000 | 46,127 to 54,047 (median 47,923) |
| internal_min | at least 15,000 | 39,828 (the boot value; it never moved) |
| int_big | at least 16,000 | 31,744 |
| psram_min | above 6,000,000 | 8,106,448 |
| App slot free | at least 20 percent | 34.8 to 35.4 percent |

All pass. No reset, panic, backtrace, stall or watchdog line. After the 24 games the unit was idle again at 50,303 bytes free, against 50,603 before the first game: no leak within the noise of the unit's own reconnect attempts. The only `E (` lines were the host asking for a tool this firmware does not have and the unit's background connection retries, both present before this work.

## What was exercised on the unit

Driven over the serial tool path (`@tool ...` on the cable), the same entry the tools use; every reply read.

- `self.game.list` names the three games with titles and scores; `start` for each answered ok; a second `start` while one runs, an unknown name and a start in full quiet each answered with a plain sentence.
- Reaction: an early tap gave "too soon" (state 4) and did not count; three rounds ended on the result screen; the average was exactly the sum divided by three (948 over three rounds gave 316) and was saved; the list showed the scores best first (lower first).
- Whack-a-mole: a bot tapped the cell that held the mole (read from the status tool); a tap on the wrong cell and a tap in an edge strip did nothing; the full run saved a score (a later bot run scored 15 of 15).
- Color memory: a bot read the sequence from the status tool and tapped it back; four rounds scored 4; a wrong color went to the end screen with the error tone queued and saved the score.
- `self.game.stop` ended a game and saved nothing; `self.game.bench_request_stop` (the lock-free path the stop word uses) ended one within a tick and answered "not running" the second time.
- `self.privacy.set` full quiet 1 ended a running game; a start was refused with "The unit is in full quiet, so no game starts. Turn full quiet off, then ask again." and worked again after quiet was turned off. (The unit stayed muted throughout; the saved state now names `home` as the source of the last change.)
- Scores were still there after a restart.
- Outside packs through `self.game.bench_install`: a damaged pack was refused with the checksum sentence; a pack named like a built-in was refused; an unsigned pack with a new name was accepted in the bench build and then started when asked by name (it showed up in `self.game.list`).
- The plain image: boots, no reader banner, no panic, the usual "wake word stays off: muted" line.

On a PC: the C core test (`host/tests/firmware/games_core_test.c`) runs under address and undefined-behavior sanitizers: parse and every refusal, the signing rule, a scripted bot playing each game to its end with fixed seeds (exact scores and timer ranges), the step budget (a looped pack stops after 65 transitions, or 6 with a pack budget of 5), the top-five table with ties and both directions, and 4,500 randomly damaged packs that must either be refused or run 400 random events without leaving their tables. A second test compiles the unit's own `update_verify.cc` and checks a pack signed by `scripts/game-pack.py` with OpenSSL (valid, other key, damaged signature, changed byte). `test_stackchan_games.py` (48 tests) also checks that each committed pack equals what the compiler makes from its table, that the compiler's refusals are plain, the patch headers, that the bench tools and unsigned packs exist only in a bench build, that nothing is allocated until a game starts, that games never call the motion code, the host names and spoken asks in both languages, the service answers with a lost or old unit, and the settings page section.

## Not verified

- A finger. No touch or swipe was made: the press handler hook, the edge rule, the bottom-swipe stop and the Games page buttons were not run (the bench tapped the same player entry the hook calls). That a non-clickable shape tree on the top layer lets a touch reach the face's handlers is how the unit's existing top-layer strip works and is expected, not proven for the game screens.
- What it looks like. No screen was seen: layout, colors, text fit and the Spanish lines are unjudged. Color memory's light and tone sync and a person's sense of the timing are unjudged.
- Sound. The unit is muted, so no tone was heard. The tone path is `maipai_sounds_play` for five shipped sounds; the game asked for 275 tones in the soak and the policy answered each (a mute refuses them). Whether five stock sounds are pleasant as game tones, and whether sounds longer than a memory step (up to about one second) queue badly, is unheard.
- The stop word. Not exercised (the microphone is off while muted). The path to the game is tested through the lock-free request, and the arming call is skipped while muted by design.
- The full memory gate turn: no spoken turn with the camera and music on was run (the unit is muted, and unmuting it is the owner's choice). The soak ran with the unit's normal idle load and a game running.
- Reaction timing accuracy: the engine measures from the 30 ms tick that fires the timer to the touch event, so a reading can be late by up to about one tick plus the screen update. It is fine for a game, not an instrument.
- A signature check on the unit: the unit's image has no update key built in (as for every dev image), so only the PC test of the same code ran. The unit refused a signed pack only by the bench path; a release image with a key was not built.
- Outside packs in a shipped build: none can be loaded there yet (see below).
- Languages other than English and Spanish: they read English text; the six-language page strings are translations written for this item and not checked by a speaker.

## Open and next

1. **Moving a signed pack to a unit.** The checks and the loader exist; the transport does not. The existing signed-update push path carries images, not small packs, and a pack over the cable's tool lines needs pieces (the bench tool takes 240 letter pieces). Decide where Home keeps the pack catalog and how the host hands a pack over (open question 2 of the design note) before this is built.
2. **Per-frame games.** None of the three needs a draw loop: the screen redraws only when the state or a counter changes. An action game that moves things every frame still needs its own measured budget, as the note says.
3. **More tones.** Five shipped sounds are all the unit can play. A short, distinct tone per color would need new clips (the phrase clips show the way: flash data, no RAM).
4. **Home catalog and sync.** Scores live on the unit. Home could read them through `self.game.scores` for a family board; nothing is built.

## Adding a game

1. Write `firmware/games/<name>.json` (copy `whack.json`: counters, states, regions, shapes, texts, rules).
2. `python3 scripts/game-pack.py build firmware/games/<name>.json -o firmware/games/<name>.mpk`, then `info` to see its size.
3. Add the file name to the list in `firmware/main/CMakeLists.txt` (patch G01) and to the table in `maipai_games.cc` (patch G02), add its names to `games.py`, and run `host/.venv/bin/python -m pytest tests/test_stackchan_games.py`.
4. To sign a pack for an outside source: `... build ... --sign update-key.pem`.
