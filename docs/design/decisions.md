# Owner decisions and corrections

All dated 2026-11-15 unless noted. Later entries override earlier ones. Each is final until the owner changes it.

## Repo and structure

1. StackChan lives in its own repo, `getmaipai/stackchan`, for visibility and its own release cadence. The `bot` repo stops being a shared framework and becomes the Reachy Mini repo when that work resumes, or is archived (2026-11-15).
2. The repo is standalone. A user never clones another MaiPai repo. The `bot` repo is not a framework (2026-11-15).
3. The host contract is a schema. This repo vendors a stamped snapshot with a CI drift check. No shared package (decision 10).
4. No Docker in our own install path. A community Compose file may exist, never required.
5. Install is explicit. No silent service. `stackchan install-service` is an opt-in autostart.
6. Names: package `maipai-stackchan`, command `stackchan`.
7. The first working origin is a local bare repository on the build machine. The GitHub repo is created when the first cloud lane starts.
8. Install from GitHub first (`pipx install "git+https://github.com/getmaipai/stackchan#subdirectory=host"` (the host is in the `host/` folder)). A PyPI listing comes later.
9. Windows service support is not in v1.
10. The capability API and record shapes are owned by `commons/spec`. Robot repos and Home vendor stamped definitions and fixtures with a drift check; they never vendor host code. There is no shared robot code repo (2026-11-15).

## Scope

11. Scope rule: the robot does what needs its body or talk loop. A feature goes to Home when it is the same for every bot, needs household records, other devices or rooms, or policy. The gray zone is limited to basics the robot must do alone, such as a timer or alarm (2026-11-15).
12. The host calls no address the owner did not configure.
13. The own-LLM brain adds no content filter of its own (2026-11-15, correction). Content safety is the connected model's job.
    Body safety stays: servo limits, volume cap, wear limits, camera-on cue, mute, pairing security.
    An optional family-friendly persona preset may ship, labeled as a prompt and not a guarantee.

## Firmware

14. Settings gesture: fix swipe up. Diagnose the touch path on a real unit first.
15. Keep one small on-device command set (stop, mute, quiet, don't move). Free RAM first, measure, then add.
16. Radio power save: yes, test on the owner's mesh Wi-Fi first. Keep it only if the unit stays connected and replies as fast.
17. Gateway fallback: remove it now, as its own revertable patch.
18. Rebase before v1 (2026-11-15, overrides "stay on the old base"). Two hops: the first upstream pin, then the newest upstream. Detail in firmware-base.md.
19. No Bluetooth. Presence comes from the network, a private-network client and the camera.
20. Sound direction is rejected. The hardware cannot do it.

## Look and feel

21. Phone app: a web app served by the host. No native app. HTTPS for push alerts via a private-network certificate or reverse proxy.
22. Face style and color are configuration. Color may be none. Defaults are neutral and uncolored until setup.
    Captions are optional on every face and off by default (correction to an earlier "on everywhere").
23. Thinking cue: visual dots always, plus a quiet tone on by default (2026-11-15, overrides "tone off"). Spoken fillers are optional and off.
24. The head touch strip drives quick sliders when `strip_mode = control`. Default is `petting`.
25. Spanish is the first non-English language. Every build step runs a language check.

## Process

26. Build trains: as few firmware builds and unit loads as possible. A train passes every host-side check first.
27. One physical unit only. The simulator is central and built first.
28. One first release with everything in v1. No tags or releases before it. Detail in release-and-updates.md.
29. Public text never mentions, compares to or credits other projects. Only the build-included notices in LICENSE, NOTICE and THIRD-PARTY.
30. An optional feature that is off costs no memory, and the memory gate proves it.
31. Ideas and designs are re-implemented in our own words. Nothing is copied that is not included in a build.

"StackChan" is the name of M5Stack's own commercial desktop robot, and a community project spells it "Stack-chan". A web search found no trademark records either way. Before a public release, search the USPTO, EUIPO and WIPO registers and decide whether the product needs its own name. Status: decided by the owner on 2026-11-15: the user-facing project name is "MaiPai for StackChan". Still run the trademark register search before the public release.

## Scope: core and Home (2026-11-15)

The core MaiPai for StackChan app is a private voice robot, simple and single purpose. Camera features, watch mode, baby and pet monitor, find my robot, remote control, live view, games, the coding companion and integrations move to MaiPai Home (tag [Home] in `features.md`). The unit keeps their body halves and the cue code path. Firmware ships as two presets from one source, `core` and `home`; feature logic for those is not kept in this public repo (it lives in Home against a capability API this repo exposes). Detail: `docs/design/features.md` ("Core and Home").

Update, 2026-11-17 (owner): the App Store test supersedes the paragraph above. Anything the stock robot or its App Center offers (photo, live view, monitoring, gallery, dance, games, remote control) may be built locally when it needs no outside service and no household data. One image carries the capabilities, opt-in and with their cues; Home keeps outside services, household records, identity and memory, policy and the child and teen gates. Details: `docs/dev/scope-core-vs-home.md`.

## Bluetooth for v1 (decided 2026-11-15)

v1 ships with Bluetooth OFF (patch 098, a Kconfig switch). After v1 lands and the memory gate passes, measure the compiled-in-but-off cost and the running cost; if flash and idle heap cost stay near the owner's 1 KB figure, add phone setup over Bluetooth (start only during setup) as a DEFER feature. Presence by Bluetooth stays dropped. The review item stays in `features.md`.

## Migration order (owner, 2026-11-15)

Finish StackChan first. Then plan the Reachy Mini migration the same way (history-preserving extraction, vendored spec copy, own repo or Home package decided at that time, memory and cue rules carried over), and retire the old `bot` repo as the last step: archive it, move anything still needed, retire `bot/AGENTS.md` and `BODY-STACKCHAN-01`, and point Home's pins at the new repos. The Reachy plan gets its own design note when StackChan ships.

## Owner decisions of 2026-11-18

These replace the 2026-11-15 scope rule and the 2026-11-17 App Store test. Where an older paragraph above says otherwise, this section wins.

1. **Boundary rule: four tests.** A feature belongs in this repository when it passes any of: (a) body: it is the unit's own hardware or cue path; (b) standalone parity: anything the stock robot or a leading community project delivers without a hub, we deliver locally as an optional package; (c) household: Home owns several-person policy, child and teen rules, recognition by name, outside services and other rooms; (d) thin connector with one owner: when paired, Home's version takes over and ours steps aside. Replaces `docs/dev/scope-core-vs-home.md` and its App Store test.
2. **A friend without Home** gets every benefit that does not need a household. The friend test (a person with a robot and a computer, no Home, no help) gates the first public release.
3. **Optional local packages allowed without Home:** Home Assistant voice and camera snapshots, agent tools, the coding companion, and local memory for several adults as plain per-person notes files (remember and forget on request). Replaces "Integrations are Home's" and "Memory is Home's".
4. **Build what is best.** Talking over the robot and a family-chosen wake word are goals. A "no" rests on physics, safety, privacy or product judgment, never on "was tried". Supersedes decision 56 and the wake-word note's "experiment".
5. **Shared concepts go into the shared spec** (movement limiter, memory admission, brain interface, indicators, vocabularies) so Reachy Mini implements the same ones. No shared robot code repository.
6. **Four users:** kid, teen, non-technical adult, technical adult. A child's or teen's robot requires Home.
7. **A 3D virtual unit**, face first, motion later, built from the real renderer.
8. **Patches stay** (decision 18). Our own firmware is not the plan; revisit only on a measured cost.
9. **One unit, minimal owner time.** One bench queue; the unit ends each window on the released image. Work does not wait on the owner.
10. **The baby monitor is scrapped (owner, 2026-11-18).** The camera is a small low-resolution sensor at about three frames a second, with no night vision, and frames do not reach the host yet. It cannot meet what a person expects of a baby monitor, and a wrong promise could do harm. We do not build, document or advertise a baby monitor or any monitoring of a child or a person who needs care. What stays: the camera as a convenience (photos, a low-resolution look at the room, motion and sound alerts for a pet or a room), each with its cue that cannot be hidden. Every user page says it is not a safety device. Supersedes the baby and pet monitor paragraphs in the 2026-11-15 scope rule and the 2026-11-17 App Store test. Reopen only if a measured camera path (resolution, rate, low light) meets the bar, with the numbers in `docs/dev/camera-quality.md`.
11. **Memory budget first (owner, 2026-11-18).** Internal RAM is the binding limit (about 64 to 70 KB free at the median, gate floor 24 KB), and the encrypted link, echo cancel, the camera stream and a custom wake word cannot all be assumed to fit together. Before more optional firmware features land, firmware measures the cost of each one and of each combination that can run at the same time, and writes one budget table (`docs/dev/memory-budget.md`): what fits at once, what is on by default, what excludes what. A feature that does not fit is cut or reshaped, not squeezed in. Landing resumes feature by feature against that table.
12. **Easy setup: three ways to get a brain (owner, 2026-11-18).** A friend picks one at first run: (a) connect to MaiPai Home; (b) use an existing stack (their own language model, speech-to-text and text-to-speech servers, with addresses); (c) install a minimal local stack (small defaults for all three, downloaded not vendored, with a plain progress page and a removal option). The host installer and the first-run page offer the three; the friend test needs all three to work without a terminal.
13. **Security defaults for v1 (owner, 2026-11-18).** The encrypted link is the default for a paired host once the memory table (decision 11) allows it; the plain link stays an explicit opt-out with a plain warning. No eFuse is ever burned (decision 14).
14. **No eFuse, ever (owner, 2026-11-18).** Nothing in our firmware, builds, scripts, installers or updates burns an eFuse: no secure boot key, no flash or storage encryption key in an eFuse, no HMAC key block, no eFuse setting of any kind, because it cannot be undone and a mistake bricks a family's robot. This replaces the earlier plan to trial eFuse-keyed storage encryption on a spare unit. Protection of the lock code, tokens and link key comes from software means that can be changed: salted slow hashing, attempt limits that survive restarts, keys derived and held in normal storage with the stated limits of that protection, and plain docs about what a person with USB access to the robot can read. A build that touches eFuses is refused by `scripts/check.sh`. Reopen only on the owner's word.
15. **Everything must fit, and resources are managed smartly (owner, 2026-11-18).** Every feature built must fit in the unit's memory together with the others that can run at the same time (decision 11's budget table is the proof). The rules: (a) load nothing that is not needed now: screens, pictures, fonts, sounds, language packs, models and tasks are created when first used and freed when closed, and an optional feature that is off costs nothing (the off-cost script proves it); (b) prefer PSRAM and flash over internal RAM, and never let a feature hold the largest internal block; (c) keep large work off the unit: pages, forms, setup and settings are served by the host's web server, not the unit's screen or firmware; heavy computation (speech, models, image analysis, translation, training) runs on the host; the unit sends and receives small events and short audio; (d) fetch on demand and cache small: assets and packs come from the host when needed (signed), and the unit keeps only what it uses; (e) one copy of anything shared (one buffer pool, one TLS session at a time, one decoder); (f) every new feature states its memory cost in its patch header and fails the gate if it breaks the budget; (g) the virtual unit enforces the same budgets in tests so a feature cannot be designed past them. When a feature cannot fit by these rules it is cut or reshaped, not squeezed in.
16. **Many robots, and nothing that quietly dies (owner, 2026-11-18).** (a) The host serves any number of StackChans at once, each with its own state, name, settings, memory, pairing and background loops; one unit's failure, slowness or disconnect never affects another, and every call names its unit. (b) The host is a real service, not a script someone started: it installs as a managed service (launchd on a Mac, systemd on Linux and a Raspberry Pi, a service on Windows if supported), starts at boot and at login, restarts itself after a crash with backoff, and is the same program whether started by hand or by the system. (c) Every part of it is supervised: a watchdog restarts a stuck or dead worker (speech, brain, pairing, update, packages), a health page and a `stackchan status` command say what is running and what is not in plain words, and a failed part shows a plain message on the settings page and, for the robot, on its screen (what went wrong and what to do). (d) The robot copes with a missing host: it keeps its local features, reconnects with backoff when the host returns, and says so on the screen when it has been away long. (e) Updates of the host keep the service running (stop, swap, start, roll back on failure). (f) Tests: kill the host, a worker and a unit connection in the middle of a turn, with two and ten units connected, and require recovery with no person acting.
17. **Installed set: the robot holds only what it uses, the dashboard chooses (owner, 2026-11-18).** Where the unit can hold only a few of something and we offer many (faces and styles, picture faces, languages, games, sounds and sound packs, overlays, personas, character packs), the unit stores a small installed set (a fixed number of slots per kind, sized by the memory budget, decision 11) and the host's dashboard is where the person picks which ones are on the robot. The host sends the chosen items as signed assets on demand (decision 15 d), swaps them without a reflash, shows how many slots are used and how much memory each choice costs, and warns when a choice does not fit. Items not in the set are not loaded and cost nothing on the unit. Sensible defaults fill the slots on first run (the person's language, the default face, a starter set of games), and a "swap" is one action. The virtual unit enforces the same slot counts.
18. **More languages, and a first screen anyone can read (owner, 2026-11-18).** (a) We add languages in tiers: Latin-script languages first with no new font (Dutch, Polish, Turkish, Swedish, Danish, Norwegian, Czech and others as translators allow), then Chinese (Simplified), Japanese and Korean through font packs, then right-to-left and shaped scripts (Arabic, Hebrew, Hindi) when the renderer supports them. (b) Fonts and strings for languages beyond the built-in set are installed-set items (decision 17): a language is a signed pack (strings plus the font glyphs it needs) the dashboard puts on the robot; the unit holds one or two at a time. (c) The very first screen is readable by anyone: a globe icon, the word for "language" in several scripts cycling or stacked, and a list where each language is written in its own script and its own name (Deutsch, Español, 中文, 日本語, 한국어), with a small flag beside it as an extra clue where one country clearly fits and no flag where it does not (a flag is never the only label, because a flag names a country, not a language); swipe pages to choose, a long list scrolls. (d) Every language shows its completeness (complete, partial with English fallback, machine draft) in the dashboard, and machine-drafted languages are marked until a native speaker reviews them.
19. **Image profiles, only if the budget proves they are needed (owner, 2026-11-18; narrowed by decision 20).** The goal is ONE image for everyone. Only if the memory budget (decision 11) shows that features cannot all fit in one image do we split them. Features that cannot all fit in one image or one memory budget (decision 11) are split into a small number of signed image profiles built from the same patch series with different feature switches (for example Standard, Voice plus with talk-over, Camera and sensors with the camera stream, IR and NFC, and Maker with the bench tools). The dashboard lists the profiles and what each adds and costs, and switches a unit by installing the chosen image through the normal signed update (the other app slot, the first-boot trial and the automatic rollback), keeping the person's settings. The unit reports its profile in its hello so the host and the dashboard always know. Rules: as few profiles as the budget forces (two is the expected number, never more than four); each has its own memory budget table, gate and bench proof; every profile contains the whole kernel and the same safety rules; assets (decision 17) stay assets and are not a reason for a profile; a combination that does not fit in one profile is not offered. The first image on a new robot is Standard.
20. **Offer a choice only when it is needed (owner, 2026-11-18).** The robot works well out of the box. We make the decisions, with good defaults, and ask the person only when the answer changes something they care about, cannot be worked out, or has a real cost. Everything else is automatic (the language from the first choice, the face and sounds from sensible starter sets, the brain from what the host finds, the installed set from use), or sits behind one collapsed Advanced section. Every setting, screen choice, profile and option must justify itself in review: who needs it, what it costs, why the default is not enough. When two options are close, we pick one. First run asks as few questions as it can (language, name, where the brain lives, and nothing else that has a default). The dashboard shows the few things that matter first.
21. **The local playground runs a simulation or a real robot (owner, 2026-11-18).** The local playground has two backends behind one interface: Simulation (the virtual unit) and Live (one of the person's registered robots, reached through their own host). Any number of robots can be registered; the playground connects to one at a time, and a robot accepts one playground control session at a time. Live mode mirrors the robot's real state (head angles, lights, screen, battery, power) in the 3D view and can send commands only through the host's normal controller path, so the movement limiter, privacy, the lock and the visible remote-control cue all apply unchanged. A live session is always labeled (the robot's name, a LIVE banner, a Disconnect button), uses a limited token scope (no lock, update or pairing tools), never shows camera frames unless the person has allowed them, and ends when the page closes. The static Pages version is Simulation only.
22. **Unit choices audit answers (owner and coordinator, 2026-11-18).** (1) Three face styles stay in the base set (big eyes, stock, minimal); the other two become installable styles (decision 17). (2) Face turning is one on/off switch, ON by default (decision 53 stands); the camera-on cue always shows and mute, lock and vision-off stop it. (3) Vision off is a tile on the quick sheet. (4) Auto lock offers off, 1 and 15 minutes, default off. (5) Quiet hours work like an iPhone Do Not Disturb: a schedule (from, to, days) plus a one-tap "Quiet now", with fixed exceptions (alarms and timers the person set always ring, the always-on safety cues never stop); the person sets it on the dashboard or the robot, and first run mentions it in one plain sentence; the default is off until set (a person chooses the hours). (6) The network test never contacts a vendor: it tests the host only. (7) First run does not ask to name the robot: StackChan is the name, changeable later on the dashboard. (8) The host sets the time zone; the unit lists zones only when no host is paired.
23. **A failed scan blocks a release (owner, 2026-11-18).** `scripts/release.sh` runs the checks, the security scan, the exposure suite and the whole test run before it builds anything. Any failure stops the release, and so does a scan or exposure step that could not run: "not run" is never a pass. Only after all of them pass does it build, sign the checksums with minisign, write a CycloneDX SBOM with syft and attach one release-evidence bundle (the gate outputs, the SBOM, the signed checksums). A `--test-key` dry run skips the gate unless asked with `--with-gate`, and its folder can never be mistaken for a real one. No GitHub Actions: it all runs locally. Detail: `scripts/security-scan.py`, `scripts/exposure-test.py`, `SECURITY.md`.
24. **Offline plan (owner, 2026-11-18).** With no host the robot mumbles (a short wordless voice) and shows captions. A content pantry of jokes, riddles and trivia lives on the unit and is refilled by the host whenever it is reachable. When a model is connected the live model answers. An offline audit lists, for every feature, what the unit does with no host and what is missing (`docs/plan/offline-audit.md`).
25. **A measured Hardware reference (owner, 2026-11-18).** One repository keeps a "Hardware reference" docs section. Every fact is marked measured, vendor-stated or inferred, and each has a source row; no vendor text is copied. It sits under the developer docs and the docs site.
26. **Quiet hours default OFF until set (owner, 2026-11-18).** Nothing is quiet by schedule until a person sets hours or presses Quiet now. This is the host behavior built on 2026-11-18 (`QuietHours`, the Quiet hours card) and the unit's SF52.
27. **Model-powered games on top of the pantry (owner, 2026-11-18).** Jokes, riddles, trivia and 20 Questions run with only a model and a robot (the own-LLM brain half); the pantry gives the offline fallback. MaiPai Home adds ratings. The host keeps the game state and the model gets no tools.
28. **First-run service button (app track recommendation, 2026-11-18, taken at the coordinator's instruction).** One button, "Keep the host running", on the first-run page and the status page. It runs the same code as `stackchan service install`, only from the host computer's own browser (never a phone), after one plain sentence that says what it writes (a login service file in your own folder; no administrator rights) and a single Confirm. There is no second choice on the page: Mac and Linux get the same button; Windows keeps the command. Because a running host that installs itself would start a second copy, the button writes the service file, starts the service and then ends this host once the new one reports healthy. Built 2026-11-18: the status page button, the detached helper (`stackchan service handover`) and the rule with its failure paths are tested with fakes; the real swap on the Studio is a bench step.
29. **The content pantry host half is a package (app track, 2026-11-18).** `host/maipai_packages/pantry/` (record, shelf writer, filter, dedupe, generator, library, sync rule, dashboard routes) is off by default, imported only when `[packages.pantry]` is on, and holds no Home code. The unit half (shelf reader, heard list, telling screens, mumble) and the `self.pantry.*` tools are the firmware track's; the sync rule runs against a unit link object until they exist.
34. **The Brain choice offers two equal routes (owner, 2026-11-18).** The first-run page and the Brain page offer **A: Hosted by M5Stack/Xiaozhi** (their servers) and **B: Custom** (your own key, a community server address, your own host or MaiPai Home, or a model on your computer), as the stock firmware does. Neither is hidden behind the other and neither is off by default as an "extra". Each route shows one plain line about where voice goes: A leaves your home for their servers; B stays where you point it. The offline fallback stays. This supersedes "off by default" in `docs/plan/m5stack-cloud-research.md` and in the hosted-brain section of `docs/user/choose-a-brain.md`. Status: planned until a test build proves their server accepts our firmware; if it does not, route A is hidden and the docs say why. Decision 20 is met: this choice is needed, because the two routes differ in who hears you.
