# Travel with the private network, 2026-11-16

Placement: unit firmware (patches TN01 to TN06) and the pinned client download (`firmware/tailnet/`). Host side needed no change. Work tree: `~/esp/stackchan-rebase/travel` (a copy of the train 3 tree). Nothing is committed.

## What it does

The unit joins the household's private network itself, so it reaches the hub from any Wi-Fi with no relay and no public address. At home nothing changes and nothing runs.

1. The hub link reports every connect. Three failures in a row (about 10 seconds) start the client, but only if a pairing key was entered or the unit joined before, and only if 46,000 bytes of internal RAM and a 24,000 byte block are free. Otherwise it says why in the log and in a `tailnet_state` event (`needs_setup`, `no_memory`).
2. Once the client is connected, the hub link swaps the saved address for the hub's private address (same port and path). The route that last worked stays; two failures in a row on it send the next connect the other way.
3. The pairing key is typed on the Wi-Fi setup page (two optional fields) or sent with `self.tailnet.set`. It is kept in the unit's own storage, erased the moment the unit has joined, and never appears in an image (patch 156 scans every build; `scripts/check-no-keys.py`). `self.tailnet.status` never returns it.
4. `self.tailnet.set` takes `enabled`, `key`, `peer`, `now` (start without waiting for failures) and `forget` (erase the key and the unit's place on the network; restart first if it runs). Turning it off takes effect at the next restart.

Several units keyed by Device-Id are unaffected: the headers and the token are not touched, and the host already reads a tailnet source address as the "away" path (`host/tests/test_stackchan_travel_host.py`).

## Build

- Switch: `CONFIG_MAIPAI_TAILNET` (default n). `sdkconfig.tailnet.defaults` turns it on with the library options; CMake adds it for `MAIPAI_PRESET=home`, for `MAIPAI_TAILNET=y`, and for any build where the client has been downloaded. `MAIPAI_TAILNET=n` leaves it out. A build with the switch on and no download stops with the two commands to run.
- Download: `bash scripts/fw-tailnet.sh` fetches the pinned client (`firmware/tailnet/PIN`) into `~/esp/maipai-deps`, outside the tree, and applies `firmware/tailnet/microlink.patch`; `source scripts/fw-env.sh` names it to the build.
- The library patch does four things: client task stacks in PSRAM (the flash-writing one stays internal), the fallback STUN host is the operator's own relay (port 3478), a port to ESP-IDF 6.1 (mbedtls 4 has no entropy objects and no ChaCha20-Poly1305 API; the WireGuard layer's own AEAD is used with the counter byte order kept; component names; IPv6 branches compile without an IPv6 stack), and compiler strictness. The old recipe was written for ESP-IDF 5.5 and could not build here.
- The byte order of the handshake port is tested on a PC against an independent RFC 8439 implementation (16 cases, `test_stackchan_tailnet_travel.py`).
- Trust: the unit's certificate bundle has no public roots (safety fix). The relay and control plane use a public authority, so TN06 adds exactly one root, ISRG Root X1 (fingerprint in the patch), when the client is built in. This is an assumption about the operator's certificates: it worked against the real control plane on the unit (below); the relay servers were not reached.

## Freeing pass (before the client)

| Step | Result |
|---|---|
| Client starts only after the hub link failed (list item 1) | at home the client costs nothing: with it linked and off, free internal RAM is the same as without it |
| Allocation threshold 512 to 256 bytes (item 6, TN04) | steady free internal RAM 53,707 (train 3 bench) to 60,0xx bytes: about 6 KB gained |
| The start task deletes itself after the client is up | its 5,120 byte stack is returned (high-water mark: 3,176 bytes left, so at least 1.5 KB headroom) |

Not done, and why: Opus stack to PSRAM (needs a 30 minute soak of the audio path), wake engine to PSRAM (needs a stop-word creation test with a person speaking), lwIP and Wi-Fi option trims (throughput risk, no one to measure it). The gate did not need them.

## Memory gate, measured on the unit

Bench build (serial tool reader and the memory line on, `MAIPAI_PRESET=home`), unit hard muted as saved (so no spoken turn, camera and music were not exercised, the same limit as the earlier gates), hub link up throughout.

| Measure | Gate | Client linked, off (11 min, 65 lines) | Client running (see below) |
|---|---|---|---|
| internal_free, steady | at least 25,000 | 59,887 to 60,139 | 40,115 to 44,531 |
| internal_min | at least 15,000 | 39,828 | 31,632 |
| int_big | at least 16,000 | 31,744 | 23,552 |
| psram_min | above 6,000,000 | 8,117,260 | 7,722,080 |
| Resets, panics, watchdog | none | none | none (11 minutes, 69 lines) |

Client running means: started with `now=true` and a key-shaped placeholder made at run time (never written to a file). The real control plane answered "invalid key" over TLS, which shows the network path, the trust root, the mbedtls 4 port and the noise handshake work up to registration. The unit then stayed in the refused/retry state, so DERP (relay) was never connected and no peer was reached. The connected state adds the WireGuard interface and peer tables; mbedtls memory is in PSRAM in this build. Its internal cost is not measured and is estimated as small against the 15 KB of headroom above the floor.

Image size, final plain build (core preset, client downloaded, no serial reader, no memory line): 3,209,008 bytes (train 3 plain: 3,095,888); free in the 5,177,344 byte slot: 38.0 percent (gate 20). Static DIRAM 163,499 bytes (train 3: 161,355). The unit now runs this plain build: read-back hash equals the build, it boots, and the log says `travel: compiled in, switch off, key none, hub address none`. Its saved key, hub address and joined mark were erased with `forget` before the flash (the placeholder run left none behind).

## Contacts (privacy page)

Only after a key is entered and the hub failed to answer: the control plane (port 443), the relay servers it names (HTTPS), STUN on UDP 3478 (the operator's relay hosts), and other devices on the same private network, directly. No address is built into the image; the hub's private address is typed by the owner and must be in 100.64.0.0/10.

## Not covered, on purpose

- Camera and avatar streams over the private path (not in the core; the camera address check wants the saved host).
- Wireless update over the private path: the unit accepts an update only from the host it is paired with by saved address.
- Switching off at run time: the client is stopped at the next restart, because a leak-tested clean stop was not built.
- A host settings field for the key: the setup page and the tool exist; the host page does not call the tool yet.
- Returning to the home route when back home while still on the private route: it stays until two failures. Harmless (the hub answers on both), but it keeps the client's memory in use until restart.

## What remains to check

A real join. It needs one pairing key from the owner (a tagged, one-time key from the private network's admin page) and the hub's private address. Then: type both on the setup page (or `self.tailnet.set`), confirm `self.tailnet.status` reaches `connected` and `joined`, join a Wi-Fi network that is not the home one, confirm the voice link opens over the private route, and run the gate again for 10 minutes in that state. Until then the travel path from DERP and peers onward is unverified.
