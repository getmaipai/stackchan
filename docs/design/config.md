# Host configuration

The host reads `~/.config/maipai/robot.toml`. On first run it copies the commented safe-default example there and prints the file location. Edit that file, then restart the host.

`brain` is `"llm"` by default. `"standalone"` is an accepted alias. The current own-LLM brain is a placeholder that returns a clear not-installed reply. `"home"` selects the Home adapter.

`[llm]` accepts `url`, `model`, `stt_url`, and `tts_url`. Leave the speech URLs absent to use the built-in local speech engines. `[home]` accepts `url`, `language`, `quiet_hours_from`, and `quiet_hours_to`; quiet-hour fields use the setting keys `household.quiet_hours.from` and `household.quiet_hours.to`. `[remote] enabled` defaults to `false`.

Unknown fields stop startup and name the key to correct or remove. `stackchan pair` prints a six-digit code for the unit setup page. The code expires after ten minutes, works once, and allows five attempts per source in ten minutes. On success the host creates the normal per-device token record. `stackchan status` shows the selected brain and paired device identifiers with last-seen time when available.

## Several robots (design, owner question 2026-11-15; built 2026-11-16 for the host, see Status below)

Today pairing already issues one token per unit, but the config has one `[llm]`, one persona and one set of settings for every unit. Several robots need per-unit settings:
- Identity: the unit already sends its own unique id, `Device-Id` (its MAC address), plus a `Client-Id` UUID, on both links; pairing keys on them. Per-unit settings are keyed by `Device-Id`; the name is a label for people. The rebuilt firmware must keep sending both on every link (patch 007, and 011 and 063 for the face link).
- The setup hotspot name is built from the same id: `stackchan-<last four of Device-Id>` (patch RM06), so two robots in setup at once never clash and the owner can tell which is which. The new base builds this name from a prefix plus the MAC (prefix `Xiaozhi` in its network code); the core firmware sets our prefix and keeps the MAC suffix. The pairing screen and the reset screen show the same short id.
- Each paired unit gets a name (`stackchan name <id> kitchen`) and an optional `[units.kitchen]` table in `robot.toml`. Any key from the top-level tables can be overridden there: `[units.kitchen.llm]` (its own model, URL, persona, key variable), language, voice, speech speed, quiet hours, face and color, night mode, volume cap, default alarms.
- Anything not overridden inherits the top-level value. Unknown unit names are an error that names the key; a unit with no table behaves exactly as today.
- Alarms and timers run on each unit (they ring with the host off), so they are per unit by nature. Recurring alarms are defined per unit in `[[units.kitchen.alarm]]` (time, days, label, sound) and pushed to that unit when it connects.
- The host keeps conversation history and the local settings page per unit; the status command and the bench page show and pick a unit.
- With Home, the same per-unit settings live in Home's robot settings and the host reads them; the brain choice can differ per unit (one on Home, one on its own LLM).
- Limits: one host serves a handful of units at once (memory and model speed decide); announcements and intercom between units are Home features.
Build: a small phase after phase 5 (config model, per-unit brain selection, per-unit history, alarm push, settings page unit picker, tests with two fake units).

Status (2026-11-16). Built: `host/maipai_body/units.py` (`UnitRegistry`) picks each unit's settings by its Device-Id, with the top-level config as the default for a unit with no settings and for an unknown unit. The voice link (`StackChanTurnBridge`) uses a unit's own model and persona when that unit saved a model URL (otherwise the Home turn client, as before), applies the unit's volume cap, and keeps each unit's history in its own brain. The avatar socket reads its unit's snapshot on connect (`AvatarServer.unit_config`). Recurring alarms are pushed to the owning unit when it connects (today's still-ahead alarms, once a day, through `self.timer.alarm`). Per-unit settings are stored in `~/.config/maipai/stackchan-units.json` through the settings page. Tests: `host/tests/test_stackchan_multi_unit.py` (two fake units). Added 2026-11-16 (second pass): `[units.<name>]` tables in `robot.toml` (required `device_id`, then `persona`, `volume_cap`, `muted`, `name`, `[units.<name>.llm]`, `[[units.<name>.alarm]]`; checked with the same rules as the settings page, with plain errors; `robot.example.toml` shows one). The table name is the unit's label unless a name was saved. Settings saved on the settings page or with the new `stackchan name <device-id-or-name> <name>` win over the table; robot.toml is never rewritten. `stackchan units` lists every known unit (paired, saved, or named in robot.toml) with its online state, read from the running host's settings page (it says "unknown" when the host is not running). The status (settings) page shows a unit picker when there are two or more units, defaulting to the only unit or the first online one. The bench takes a unit on every control (head, lights, brightness, privacy including camera, sound, face, the generic tool caller, chat speak) and lists units at `/api/units`; with no unit named it uses the only unit, or the first online one, and with several offline it asks for a pick. Tests: `test_stackchan_units_config.py`. Not built: attaching live unit drivers to `stackchan bench` (it still runs only with `--sim`; a test passes two fake units through `BenchServer(units=...)`), and per-unit firmware versions with two units connected (see `docs/dev/updater.md`).
