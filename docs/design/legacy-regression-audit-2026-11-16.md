# Legacy regression audit (2026-11-16)

Question from the owner: the original firmware already fixed speed, background-noise false triggers, random head movement, stutter and more, and the rebuilt firmware lost those fixes. This is a read-only audit of every legacy patch against the current `firmware/patches/ORDER`. Nothing was built, flashed or run on a unit, so every "effect" below comes from the patch text and the host logs it quotes, never from a measurement. Where the effect cannot be known from text, the row says so.

Paths: legacy patches are in `host/maipai_body/bodies/stackchan/firmware/patches/` (called LEG below); the rebuild carries `firmware/patches/` (called CUR). Cut verdicts are from `docs/design/firmware-v1-cut.md`.

## 0. What the audit found, in six lines

1. The owner is right that fixes were lost, but not the ones the list in the request names. No legacy patch tunes the voice-activity threshold, Opus pacing, buffer sizes for speed, task priority, TLS or connect time. Speed in the legacy series came from only four things, all of them still in CUR: 003 (persistent socket, no connect per turn), 014 (Wi-Fi awake while speaking), 016 (open speech at tts start), 075 (power save NONE while the link is down, MIN_MODEM instead of MAX_MODEM when idle). All four are ALREADY-HERE.
2. The noise-trigger work in the legacy series is one patch: 083 (wake front end with no echo reference). It is DEFER in the cut and absent from CUR. This is the single biggest regression found.
3. Stutter and freeze work lives in 053 (stop word off, stacks back in internal RAM), 058 (RAM trims) and 077 (silent link close). 077 is here. 053 and 058 are not, and CUR ships the exact configuration 053 was written to undo (stop word live, AFE detection task stack in PSRAM).
4. Random head movement: the firmware side (037 stillness default, 038 move cap) is ALREADY-HERE. What still moves the head today is host code and two firmware features added after the rebuild (section b, causes 8).
5. Tap does nothing: 081 (IMU-assisted head tap) is CORE-V1 in the cut, yet it is not in CUR, while CUR keeps 080 (a weak touch needs 32 samples). A light tap on the head can not register.
6. Wake word dropped: 032 is CORE-V1 in the cut and absent from CUR. Whether the new base already has the fix cannot be known from text (section a, row 3).

## b. The ten most likely causes of the current complaints

Each cause is a hypothesis from text. The "check" is the cheapest test that would confirm it.

1. **Wake word goes deaf after hours, or fires on residue: wake front end still runs the echo canceller with a second microphone as the reference.** Patch 083. Complaint: wake word not responding, and possibly talks on room noise (the legacy log showed the voice detector firing "on the residue" while the wake model got "a hollowed-out word"). Check: boot log AFE line shows an AEC stage with 2 channels (1 microphone, 1 playback), and `wake_selftest` passing right after boot but failing after hours.
2. **Wake word heard then dropped with no state change.** Patch 032. Complaint: wake word not responding while the log says "Wake word detected". Check: serial log after saying the word shows no idle to connecting change.
3. **Freezes of 30 to 45 s and cut-off speech: stop word live with a PSRAM stack on the AFE detection task.** Patch 053 (and 058 for the RAM that keeps the stop word armed). Complaint: stutter, slow, "talks then stops". Check: the memory gate line (TN05) shows internal free below 34 KB at boot; `stop_word` event state; the same stall with the stop word compiled off.
4. **A freeze with no record of why.** Patches 084 and 070. R02 and R04 now restart the unit out of a freeze, but nothing records the cause, and nothing tells network stutter from decoder stutter. Complaint: stutter and "sometimes it just stops". Check: after the next stall, no `coredump` event and no `playback` gap counts exist to read.
5. **Light tap on the head does nothing.** Patch 081 absent, 080 present (a one-pad reading needs 32 samples, two seconds). Check: a quick tap on the strip logs no `head_touch`; a strong press does.
6. **Tap on the screen does nothing.** Not a legacy loss: CUR 105 is the later "tap" design. A tap on the mouth toggles mute, on an eye toggles vision, on the forehead toggles full quiet, and those regions never start a listen. A tap on those three spots looks like "does nothing" (or like a mute the owner did not ask for). Legacy 105 used hold (0.5 s). Check: tap the cheek area, not the mouth, eyes or forehead.
7. **Dim screen does not wake.** W01 (new, 2026-11-16) fixes the four-link cause. It is in ORDER, but only the host side of the legacy had a dim path; verify the flashed image is the one that contains W01 and that the saved level is not the dim level from before. Also legacy 074 raised the idle shutdown to 3600 s, which CUR lacks (rank 10): a unit that lost the host powers off in ten minutes. Check: `self.screen.get_level` (saved and live) after the screen dims.
8. **Keeps looking around.** Firmware stillness is intact (037 default off and saved, 038 cap of 40 moves a minute). The movement now comes from: the host look-around (`bodies/stackchan/head_search.py`: reasons "person", "speaker" and "dark", owner-approved 2026-11-12), person tracking (`person_tracker.py`), the speaker turn (`speaker_gaze.py`), word reactions in U02 (a word such as "love" plays a built-in dance, including look_around), and music dance V03 (off unless `robot.dance.auto` is on, default off). Legacy had none of these. The head gate (`head_gate.py`) logs who moved the head: the host log names the source. No legacy patch fixes this; it is a host or design question.
9. **Talks on fan noise.** No legacy firmware patch gates noise. The gate is host side: `host/maipai_body/speech/noise_gate.py` (levels low, medium, high; "a fan, a kettle or the room's hiss can wake a speech engine into inventing 'thank you'") and the follow-up window in `speech/follow_up.py` (default 8 s with no wake word, which re-arms listening in a noisy room; legacy 034 lets the host end it and is in CUR). Combine with cause 1 (residue). Check: which noise gate level is set, and whether the follow-up seconds setting is above zero.
10. **Slow reply.** All four legacy speed fixes are in CUR, so slowness is not a lost patch. Candidates the text can not rank: a weak access point joined (044, upstream claim unverified), a face update loop change (H02 removed a 100 ms sleep that held the screen lock; fine) and the travel link probes (TN01 to TN07) running when the home address is slow, plus real model latency on the host. Check: host log turn timestamps (wake to first audio) split into link, model and playback; the Wi-Fi event RSSI.

## e. What this audit did not do

No source tree was built, so every "absent from CUR" is a grep over the patch files, not over the applied tree. A change hidden in B01 (which records 11 edits to the vendor tree that "never were in a patch") would not show in a grep of patch names; B01 was read for the wake path, the audio codec gain and the power-save lines, and no echo or stack-size edit was found there. No unit was flashed. Effects on speed are not measured anywhere in the legacy text except where a patch quotes a host log; the strip-results note says no latency comparison, soak or stop-word allocation check was done on the rebuild.
